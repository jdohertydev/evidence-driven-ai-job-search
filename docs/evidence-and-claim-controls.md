# Evidence and claim controls

The application stage is evidence-constrained. Persuasive wording is useful only if the underlying claim is accurate and defensible.

## Source hierarchy

Different sources answer different questions:

| Source | Used for |
|---|---|
| Job advert | Requirements and employer-stated expectations |
| Employer research | Business context and role environment |
| Career-history records | Employment, responsibilities and historical examples |
| Qualification certificate | Exact award title, grade and date |
| GitHub repositories | Project scope, technologies, testing and documentation |
| First-person input | Motivation, preferences and judgement |

When sources conflict, the more authoritative source wins for that type of claim.

## Claim rules

The workflow explicitly rejects common forms of inflation:

- **Exposure ≠ expertise**
- **Project work ≠ commercial experience**
- **Learning ≠ certification**
- **Prototype ≠ production system**
- **Familiarity ≠ mastery**
- **AI-assisted development ≠ wholly unaided authorship**

If evidence is missing, the claim is removed, qualified or recorded as a gap.

## Example

| Candidate statement | Evidence state | Treatment |
|---|---|---|
| Built a VBA tool to improve a staff workflow | Supported by career history | Use |
| Built an n8n/OpenAI workflow with testing and human review | Supported by public project | Use |
| Experienced Power Automate developer | No direct project/employment evidence | Do not claim |
| Familiar with Microsoft tools through previous work | Supported, but broad | Qualify precisely |

## Final audit

Before recommending an important sentence for submission, I use five questions:

1. Is it true?
2. Can I evidence it?
3. Is it relevant to this role?
4. Is it stronger than the available alternative?
5. Could I defend it if challenged in an interview?

A sentence that fails any of those tests should not survive merely because it sounds good.
